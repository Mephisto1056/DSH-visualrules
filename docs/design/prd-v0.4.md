## 1. 背景与问题

DSH 以工作区为单位组织开发，每个工作区对应不同的仓库或团队。各团队的开发规范、Git 提交策略、服务器环境都不一样，但 DSH 里没有统一的地方展示这些信息，导致：

- 切换工作区后，不清楚当前该遵守哪套规范。
- 容易用错 Git 身份（邮箱、用户名）提交代码。
- 看不到当前项目连了哪台服务器、用什么账号登录，存在误操作生产环境的风险。
- 团队规范散落在 CONTRIBUTING.md、commitlint 配置、群公告里，AI 写代码时完全不知道。
- 现有 Git Tree 类插件体验差，连基本的提交图谱查看都不如 VS Code 的同类插件。

## 2. 目标与非目标

### 2.1 目标

1. 为每个工作区提供一份"档案"，切换时自动展示，做到**看得到**。
2. 在提交前做校验和提醒，做到**管得住**。
3. 把团队与项目规范注入大模型，不修改 DSH 的 agents.md，做到**守得住**。
4. 提供好用的 Git 图形视图，让每次提交都是可追溯的真实索引。
5. 团队规范随仓库共享，个人信息留在本地；规范可跨工作区复用；所有功能均可选。

### 2.2 非目标（v1 不做）

- 不做完整的 CI/CD 平台、代码托管平台或项目管理系统。
- 不存储、不同步任何明文密码、token、私钥内容。
- 不替代 Git 命令行的全部能力（如复杂的交互式变基 UI，放后续版本）。
- 不做跨工作区的团队级统计与报表。
- **不做服务端保护**：本地校验是辅助，替代不了远端分支保护和 CI。

## 3. 目标用户与场景

**目标用户**：同时在多个工作区、多个团队之间切换的开发者（首要用户为作者本人）。

**典型场景**

| 场景 | 期望 |
| --- | --- |
| 早上打开 DSH，切到团队 A 的工作区 | 会话头部入口的环境色点变色，一眼看出当前身份、环境、分支 |
| 点会话头部入口 | 侧栏弹出快速预览：Git 身份与来源、连接信息、环境标识、Git 规范摘要 |
| 想看得更全 | 从预览面板跳转到整页档案 |
| 准备提交代码 | 自动检查邮箱、分支名、commit message 是否合规，不合规给出明确提示 |
| 准备在 main 上直接提交 | 提交前拦截，并建议走 PR 流程（push 由你自己二次确认） |
| 连接到生产服务器 | 醒目的红色环境标识，高危操作二次确认 |
| 想看项目历史 | 打开 Git 图形视图，清晰查看分支、合并、提交详情 |
| 新建工作区 | 选择团队模板，一键套用规范配置 |
| 新开一个会话 | 自动带上该工作区启用的规范，模型按团队规范写代码、做提交 |

## 4. 功能清单

优先级：P0 = MVP 必做，P1 = 第二期，P2 = 后续规划。

### 4.0 规范注入（核心模块）

规范注入是这个插件的核心价值：每个项目、团队的规范文档由插件管理，并在会话中注入大模型，不改动 DSH 的 agents.md（官方会持续更新，且各项目规范不同）。

| 编号 | 功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| F0.1 | 规范包管理 | 一份规范 = 一个或多个文档（开发规范、Git 规范、评审要求等），可新建、导入、编辑 | P0 |
| F0.2 | 会话注入 | 会话启动时，把当前工作区启用的规范包追加进模型上下文，不修改 agents.md | P0 |
| F0.3 | 分层与覆盖 | 个人通用规范 → 团队/项目规范 → 工作区覆盖，后者覆盖前者，冲突时标注来源 | P0 |
| F0.4 | 跨工作区复用 | 规范只存一份"全局规范库"，各工作区只引用不复制，改一处全部同步 | P0 |
| F0.5 | 注入预览 | 启用前可查看最终拼出的完整注入文本及其长度 | P1 |
| F0.6 | 按需开关 | 每个规范包、每个工作区都可单独启用或关闭，默认全部关闭 | P0 |

> **实现口径（已验证，见 §10.1）**：注入通过 `systemPrompt` 服务按会话作用域注册，不触碰 agents.md；内容随会话的当前目录解析，改配置在下一轮请求生效。

### 4.5 UI 落点与交互

本节回答"这些信息长在哪"。DSH 的界面由可注册的插槽组成，插件只能挂到真实存在的插槽上，因此每个模块都要指定落点。

#### 4.5.1 落点分配

| 落点（DSH 插槽） | 承载内容 | 性质 |
| --- | --- | --- |
| 会话标题栏 `conversation.session.header.utilities` | F1.8 会话头部入口：小图标 + 环境色点 + 角标，点击打开右侧栏快速预览 | 按会话，右上角工具区 |
| 右侧 sidebar `rightbar` | 点击入口后的快速预览面板（F1.1、F1.3–F1.5 摘要） | 按会话，可开合 |
| 侧栏图标 + 整页 `sidebar.panellist` + `main` | 完整档案页（F1.1–F1.7 全部）；左侧栏图标是全局常驻入口 | 全局入口，独立页面 |
| 设置页 `settings.section` | 规范包管理（F0.1）、配置表单（F4.6） | 全局入口 |

#### 4.5.2 会话头部入口

- 位置：会话头部右上角工具区 `conversation.session.header.utilities` 的最左侧，一个 28×28 的图标按钮 + 一个环境色点；不再占用底部通栏。
- 颜色语义：图标保持中性色，环境色点按 dev 中性灰 / test 蓝 / staging 黄 / prod 红区分；prod 常驻脉冲强调，不可被忽略。
- 角标：存在未处理的校验告警时显示数字角标。
- 降级：当前目录不是 Git 仓库时图标变灰，点击仍打开快速预览并展示"当前工作区没有仓库"；无配置时不显示角标。
- 悬停：一行 tooltip「工作区名 · 环境 · 身份邮箱」。
- 点击：打开右侧 sidebar 的快速预览面板（见 4.5.3）。再次点击关闭。
- 可见性：会话头部工具区在有会话时显示；空白 Hero / 未打开会话时不显示。完整档案页仍由左侧栏 `sidebar.panellist` 图标常驻进入。

#### 4.5.3 侧栏快速预览

从会话头部入口打开，右侧 sidebar 中呈现，目标是一屏看完、不用跳转：

1. **身份**：user.name / user.email + 来源（全局 / 仓库级）。
2. **分支**：当前分支、与远端的领先/落后数、受保护分支警示。
3. **环境**：环境标识 + host 与登录用户名（F1.2 开启时）。
4. **规范摘要**：分支命名、commit 格式、受保护分支、Review 要求（只列规则要点，不展开全文）。
5. **注入状态**：当前启用了哪几个规范包、合计字符数（对应 F0.5 的轻量版）。
6. **出口**：底部两个操作——「打开完整档案」「编辑配置」。

交互约定：

- 打开即刷新，数据走缓存 + 后台刷新，300ms 内先出骨架再填数。
- 只读，不提供任何写操作；所有修改跳转到整页或设置页。
- 面板宽度跟随 DSH 右栏，不做独立宽度控制。

#### 4.5.4 风险与降级

- `conversation.session.header.utilities` 是**列表插槽**，可与内置和其他插件入口共存；本插件以 `order: -20` 排在右上角工具区最左侧。若该插槽不可用，入口仍可从左侧栏的 `sidebar.panellist` 图标进入完整档案。
- 右侧 sidebar 入口已验证：通过 `sidebarRightTabs` + `sidebar.right.pane.tab` 注册原生标签页；`sidebarRight` 不可用时回退到浮层 `shell.overlay`，内容与交互保持一致。

## 5. 配置与存储设计（草案）

配置分三层，各自有明确的存放位置和写入方。**插件不读也不写 DSH profile 的 `cordis.patch.yml`**，那是用户自己的配置文件。

**团队层（仓库内 `.dsh/profile.yaml`，入库，插件只读）**

```yaml
version: 1
team: 支付平台组
git:
  branch_pattern: "^(feature|fix|hotfix)/[a-z0-9-]+$"
  commit_format: conventional
  require_issue: true
  merge_strategy: squash
  protected_branches: [main, "release/*"]
  review:
    min_approvals: 2
dev:
  toolchain: { node: "20.x", python: "3.11" }
  lint: eslint
  ci_required: [lint, unit-test]
docs:
  wiki: https://example.com/wiki
  issues: https://example.com/board
environments:
  - { name: staging, host: stg.example.com, level: warn }
  - { name: prod, host: prod.example.com, level: danger }
```

**个人层（DSH 本机存储，不入库，插件读写）**

```yaml
# 按工作区目录索引；密钥只存引用名，不存内容
identity:
  git_name: 李若宇
  git_email: me@company-a.com
servers:
  staging: { user: ruoyu, key_ref: dsh-ssh-a }
  prod:    { user: ruoyu_ro, key_ref: dsh-ssh-a }
exclusive:
  packs: [personal/general]   # 本工作区额外启用的个人规范包
```

**规范库（DSH 本机存储，跨工作区共用）**

```yaml
packs:
  personal/general:  { title: 我的通用习惯, updated: 2026-11-08 }
  team-a/git-rules:  { title: 团队 A 提交规范, updated: 2026-10-30 }
workspace_overrides:
  /Users/ruoyu/code/pay-core:
    packs: [team-a/git-rules, team-a/coding-style]
```

要点：

- 团队层只能引用**团队自己的**规范包；个人包只在个人层启用，避免把个人偏好提交进仓库。
- 个人层不进入仓库，因此天然不需要加入 `.gitignore`；只在检测到个人字段出现在团队层时告警。
- 规范包正文与个人配置都存在 DSH 存储里，插件卸载后不残留文件。

字段名仅为示意，最终以 DSH 插件配置规范为准。

## 6. 边界需求

### 6.1 安全边界

- 不保存明文密码、token、私钥内容，只保存引用（密钥名、系统凭证管理器的 key）。
- 个人层存于 DSH 本机存储，不进入仓库；检测到个人字段出现在团队层时告警并拒绝使用该字段。
- 服务器信息仅用于展示和校验，插件本身不主动发起连接或执行远程命令（v1）。
- 绕过校验的记录只保存在本地。

### 6.2 权限边界

- 对仓库内容只读；写操作仅限用户在图形视图中主动触发的 Git 命令。
- 团队层配置只读展示，修改走正常的仓库提交流程。
- **Git 钩子是唯一的仓库内写操作**，必须可选、显式安装、可一键卸载；安装前展示将写入的路径与内容，已存在同名钩子时串接而不覆盖。
- 不读取工作区以外的文件（唯一例外是团队层配置指向的、用户明确选择联动的规范文件）。

### 6.3 校验边界

- 本地校验是提醒与辅助，**不能替代**服务端的分支保护和 CI。文档中需明确说明：`git commit --no-verify` 可以绕过本地全部检查。
- 校验失败时必须给出：违反了哪条规则、规则来源、如何修正。
- 规则解析出错时，降级为只展示、不拦截，不能因为插件自身出错阻塞用户提交。

### 6.4 兼容与降级

- 工作区没有配置文件时：只展示自动探测到的信息（Git 身份、分支、remote），并提示创建配置。
- 非 Git 目录：会话头部入口变灰，隐藏 Git 相关模块。
- 多仓库（monorepo / 多 root）工作区：按子目录分别展示，规则可按路径覆盖（P2，v1 不做）。
- 配置文件版本字段：向前兼容，未知字段忽略并提示。
- 右侧 sidebar 入口不可用时：回退到浮层，功能等价（见 §4.5.4）。

### 6.5 性能边界

- 点击会话头部入口到预览面板出骨架 < 300ms（不含 Git 子进程耗时）；数据填充不阻塞骨架。
- 身份与分支信息走缓存，切换会话时后台刷新，不做同步阻塞读取。
- Git 命令在后台执行，不阻塞 UI；长任务可取消。
- 实时状态类功能（F1.9）使用轮询或事件，且可关闭。
- Git 图谱的性能指标（10 万提交、首屏 < 1s）属于 §4.3 独立评估的范畴，不作为本插件的验收项。

### 6.6 不做清单

- 不自动修改用户的 Git 全局配置。
- 不自动替用户修正 commit message 或分支名（只提示，可提供一键复制建议）。
- 不上传任何数据到外部服务。
- 不实现 Git 图谱（v1）。

### 6.7 注入与拦截时机边界

- 拦截只发生在 commit 前；push 由用户自己二次确认，插件不拦截。
- 注入不修改、不覆盖 DSH 的 agents.md，只在会话层追加；关闭或卸载插件即恢复原样。
- 注入内容设长度上限，超出时按层级优先级截断并提示，避免挤占模型上下文；上限按真实上下文预算换算，不写死字符数。
- 注入内容启用前可预览；规范冲突时按层级覆盖，并标注来源。
- 规范文档中不放密钥、账号等敏感信息；注入只对启用它的工作区生效。
- 配置变更在**下一轮模型请求**生效，不追溯改写已发生的对话；关闭同理。
- 所有功能默认可选，未启用的功能不读取任何相关数据。

## 7. 非功能需求

- **可用性**：核心信息一屏可见；生产环境提示必须无法被忽略。
- **可靠性**：插件异常不影响 DSH 与 Git 本身的正常使用。
- **可扩展性**：校验规则以插件化方式组织，后续可新增规则类型。
- **可观测性**：本地日志记录规则命中与异常，便于排查。
- **可卸载性**：卸载后不留配置残留、不留 Git 钩子、不改动仓库内容。

## 9. 验收标准（MVP）

1. 切换到任一工作区，1 秒内看到正确的 Git 身份与来源、环境标识；启用服务器信息时，同时看到连接信息。
2. 会话头部入口的环境色点随环境变色；点击后 300ms 内出现预览面板并填出身份、分支、环境、规范摘要。
3. 用错误邮箱提交时，能按配置级别警告或拦截，并说明原因；说明能被模型读懂并据此自行修正。
4. **AI 通过命令提交时同样被拦截**：在受保护分支上由 AI 发起的 commit 被拒绝，模型在下一轮能读到违反的规则并改正后重试。
5. 在受保护分支上直接提交时被提示或拦截，并说明正确流程；push 不被插件拦截。
6. 启用规范包后，新会话的模型能按该规范行事，且 DSH 的 agents.md 保持原样；关闭后下一轮恢复。
7. 同一份规范包被多个工作区引用，修改一处，所有引用处同步。
8. 无配置文件、配置出错、非 Git 目录三种情况下，插件均不报错、不阻塞。
9. 个人配置不出现在仓库变更列表中。
10. 卸载插件后，Git 钩子被移除，仓库内容无改动。

## 10. 技术结论与待确认问题

### 10.1 已验证结论

**结论一：规范注入可以不改 agents.md（原疑问 1，已验证）**

DSH 提供 `systemPrompt` 服务的注册能力，可以在**会话作用域**内注册一段提示内容：

- 注册在会话作用域下，只对该会话生效；注册与销毁都会通知框架刷新提示词。
- 提示词每个请求步骤重新组装，因此**改配置在下一轮生效**，不需要重开会话；关闭同理。
- 不修改、不依赖 agents.md，卸载即恢复。

两个实现约束（写进设计要求，不再作为待确认项）：

- 提示内容的上下文里**不包含会话标识**，所以必须按会话作用域注册，不能注册成全局。
- 决定"注入哪套规范"的依据是**会话的当前目录**，而当前目录在会话中可以被切换（含切到 worktree）。因此注入内容要跟随目录变化重新解析，不能只在会话创建时算一次。

**结论二：提交拦截需要两层，单靠一层覆盖不全（原疑问 2，已验证）**

- **工具层**：在工具执行前拦截，能拦住 AI 通过命令执行的提交，并且拒绝原因会作为工具失败结果返回给模型，模型下一轮可读、可改。这同时是 F2.8 的落点。
- **工具层的缺口**：交互式终端里输入的提交、脚本或构建命令里间接发起的提交、后台任务中延后执行的提交，工具层都看不到。
- **仓库级 Git 钩子**：覆盖上述全部缺口，也覆盖用户自己在终端或 IDE 里的提交。这是唯一能保证"commit 前一定经过检查"的机制，代价是必须往仓库里写钩子（见 §6.2 的约束）。
- **无法覆盖的部分**：`--no-verify` 绕过、以及其他机器上的提交。这一点在 §6.3 里对用户明示。

**结论三：团队层与个人层必须物理分离（原 §5 的隐含问题，已修正）**

插件不能改写 DSH profile 的配置文件，个人层因此不能放在那里；规范库也需要一个跨工作区的持久位置。二者统一落在 DSH 本机存储中，团队层只保留仓库内的只读配置。

### 10.2 待确认问题

1. **右侧 sidebar 的插件入口**：已确认。使用 `sidebarRightTabs` + `sidebar.right.pane.tab` 注册原生标签页；`sidebarRight` 不可用时按 §4.5.4 回退到浮层。
2. **服务器信息的读取来源**：已采用插件自维护方案——团队层 `environments` 提供 host/端口/跳板机，个人层 `servers` 只存登录用户与密钥引用名；不读取 DSH 连接管理，也不读取工作区外文件。
3. **Git 图谱渲染方案**：待独立评估后确定；产品要求是对标 VS Code 主流 Git 图谱插件。客户端侧没有 JSX 转换、也没有第三方依赖可用，这是成本的主要来源。
4. **非 Git 版本控制**：做成可选适配层，v1 只做 Git 并预留接口，是否 v1 就要请确认。
5. **AI 提交标记的落地形态**：是用本地索引记录"哪个会话提交了哪个 hash"，还是写进提交附注（可移植但需要模型配合）。倾向本地索引，v1 先做数据层。

> 第 1、2 条已决，保留在此作为结论记录；第 3–5 条仍待确认。

## 11. 术语

本文里的"工作区"容易和实现层的概念混淆，统一如下：

| 说法 | 含义 |
| --- | --- |
| 工作区 / 项目 | 用户视角的一个代码目录 |
| 会话目录（cwd） | **实现层真正决定注入和校验依据的东西**：会话当前所在目录，可被切换 |
| 仓库 | 包含 `.git` 的目录；一个工作区可能包含多个仓库 |

产品文案继续说"工作区"，但所有实现判断一律以会话目录为准。
